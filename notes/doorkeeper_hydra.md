### DoorkeeperとORY Hydraの比較

| 比較項目 | Doorkeeper | ORY Hydra |
| :--- | :--- | :--- |
| **役割** | Railsアプリケーションに組み込まれる**OAuth 2.0認可サーバーGem**。認証と認可の両方をアプリケーション内で処理します。 | 認証ロジックを持たない**純粋なOAuth 2.0認可サーバー**。認証は外部のサービス（既存のRailsアプリなど）に委ねます。 |
| **アーキテクチャ** | **密結合**。既存のRailsアプリケーションと一体化して機能します。 | **疎結合**。Railsアプリケーションとは別の独立したサービスとしてデプロイ・運用します。 |
| **実装のしやすさ** | **容易**。Railsの慣習に従って開発でき、既存の`User`モデルや認証ロジックをそのまま活用できます。 | **複雑**。Hydraのデプロイ・運用に加えて、RailsアプリからHydraのAPIを呼び出すための実装（ログイン画面のリダイレクトや認証結果の送信など）が必要です。 |
| **学習コスト** | **低い**。OAuth 2.0の概念の理解は必要ですが、DoorkeeperのドキュメントとRailsの知識で対応可能です。 | **高い**。OAuth 2.0/OIDCの深い知識に加え、HydraのアーキテクチャとAPIの仕様を理解する必要があります。 |
| **運用コスト** | **低い**。既存のRailsアプリケーションの一部として運用できるため、特別なインフラや運用体制は不要です。 | **高い**。Hydraサーバーを別途デプロイ・運用する必要があり、コンテナ化やスケーリング、監視などのインフラ管理が必要です。 |
| **スケーラビリティ** | **中程度**。Railsアプリケーションのスケーラビリティに依存します。認証・認可の負荷が高くなると、アプリケーション全体の性能に影響を与える可能性があります。 | **高い**。認証（Railsアプリ）と認可（Hydra）が分離しているため、それぞれ独立してスケールできます。大規模なマイクロサービスアーキテクチャに適しています。 |
| **カスタマイズ性** | **高い**。Railsアプリケーションのコード内で自由にカスタマイズできます。 | **非常に高い**。Hydra本体は変更しませんが、認証・認可のロジックを担うRailsアプリケーションは自由に構築できます。 |
| **利用シーン** | - 比較的小規模なサービス間のSSO<br>- 既存のRailsアプリに手軽にSSO機能を追加したい場合<br>- 開発リソースや運用リソースが限られている場合 | - 大規模なサービスや複数のサービスを展開している場合<br>- 将来的な拡張性やスケーラビリティを重視する場合<br>- 厳格なセキュリティ要件がある場合<br>- 認証・認可基盤をマイクロサービスとして独立させたい場合 |
